Q1 · system designthe one they built the role around

"Design an automated build-failure analysis and self-healing platform."

OpenClose

Framework: talk in this order

  1. Ingest. Jenkins and node agents emit build.failed and node health metrics to Kafka; logs land in Splunk or object storage, keyed by build ID.
  2. Triage, cheap first. A deterministic classifier matches known failure signatures (regex, error codes, exit status) before any LLM call. Most build failures repeat.
  3. Diagnose. The agent pulls only the error window (error ± N lines, not a 200 MB log), node metrics and recent changes, then retrieves similar past incidents.
  4. Remediate. A planner proposes steps from an allow-listed runbook catalogue (clear cache, reinstall toolchain, reimage, drain); an executor runs them through tools, never raw shell.
  5. Validate and rerun. Health checks, then rerun the build. Success writes the resolution back to memory; failure escalates with full context.
  6. UI. A React dashboard of failures, agent reasoning traces, approve/reject for risky actions, and MTTR trends.

Tradeoffs to say out loud

latency vs accuracy

Signature match in milliseconds handles repeats; the LLM only sees novel failures.

cost vs context window

Error-window extraction plus retrieval beats stuffing whole logs: cheaper, with less hallucination.

autonomy vs blast radius

Auto-run low-risk, reversible actions; human approval for reimage, drain, or anything touching many nodes.

on-prem constraint

Azure OpenAI goes through an approved gateway; deterministic paths keep working if the model is down.

Q2 · agentic AIagent-to-agent + safety

"How do agents communicate, and how do you keep autonomous remediation safe?"

OpenClose

Framework

  • Two communication styles. Orchestrated (a supervisor or graph like LangGraph or AutoGen GroupChat routes between agents, good for one incident's reasoning) and choreographed (agents react to Kafka events, good for decoupling and scale). Use both: Kafka between stages, a graph inside diagnosis.
  • Typed contracts. Agents exchange schema-validated JSON, not free text. Each message carries incident ID, confidence and evidence.
  • Safety layers. Tool allow-list, parameter validation, dry-run mode, rate limits per node and per farm, a circuit breaker if remediation success drops, idempotency keys so a replayed event never reinstalls twice, and a full audit trail.
  • Confidence gating. Below threshold, or a novel failure class, goes to a human via the React UI or a ticket.

Tradeoff to say out loud

specialization vs moving parts

More agents means sharper roles but more latency, cost and failure points. Start with three or four (triage, diagnose, remediate, validate) and add one only when evals show a gap.

Q4 · troubleshootingroot-cause analysis

"A build fails on one node but passes on others. How do you diagnose it?"

OpenClose

The RCA ladder

  1. Scope. One node or a pool? Since when? Correlate with the last change: OS patch, toolchain version, config push, new job type.
  2. Diff the node against a healthy one: disk space and inodes, memory, CPU steal, toolchain and dependency versions, env vars, file permissions, network and DNS to the artifact repo.
  3. Read the evidence. The first error in the log, not the last; exit codes; Grafana or Dynatrace metrics around the failure time.
  4. Reproduce and fix. Rerun pinned to that node vs a healthy node; apply the smallest reversible fix; validate; rerun.
  5. Prevent. Add a signature to the classifier and a health check so the agent catches it next time.

Q5 · engineeringthe manager named Python + Kafka

"How would you use Kafka in this system?"

OpenClose

Framework

  • Topics: build.events, node.metrics, incident.diagnosed, remediation.requested, remediation.result, plus a dead-letter topic.
  • Partition key = node ID. Every event for one node stays in order, so two agents never remediate the same node concurrently.
  • Delivery. At-least-once with idempotent consumers (dedupe on event ID); commit offsets manually, only after the action is recorded.
  • Consumer groups. One group per agent role; scale each horizontally.
  • Replay. The log is the audit trail, and it lets you rerun an improved agent against last week's failures as an offline eval.

Tradeoffs to say out loud

ordering vs parallelism

More partitions, more throughput; ordering holds only within a key.

exactly-once vs simplicity

Prefer idempotency over Kafka transactions unless a write spans topics.

remediation_service.py · hardened endpoint the executor calls
import subprocess                                    # run fixed scripts; never with shell=True
from enum import Enum                                # closed set of allowed values
from fastapi import Depends, FastAPI, Header, HTTPException  # framework, DI, header param, errors
from pydantic import BaseModel, Field                # schema validation for the request body

app = FastAPI()                                      # the remediation microservice

class Action(str, Enum):                             # allow-list: the agent may request only these
    CLEAR_CACHE = "clear_cache"                      # low risk, reversible
    REINSTALL_TOOLCHAIN = "reinstall_toolchain"      # medium risk, still scripted and reviewed

RUNBOOK = {                                          # each action maps to one fixed, code-reviewed script
    Action.CLEAR_CACHE: ["/opt/runbooks/clear_cache.sh"],
    Action.REINSTALL_TOOLCHAIN: ["/opt/runbooks/reinstall_toolchain.sh"],
}

class RemediationRequest(BaseModel):                 # anything that fails this schema gets an automatic 422
    node_id: str = Field(pattern=r"^[a-z0-9-]{1,64}$")  # blocks injection like "node1; rm -rf /"
    action: Action                                   # must be one of the enum values above
    incident_id: str = Field(max_length=64)          # doubles as the idempotency key

COMPLETED: dict[str, dict] = {}                      # demo only: use Redis or a DB table in production

def verify_caller(x_service_token: str = Header(...)) -> str:  # reads the X-Service-Token header
    if not is_valid_service_token(x_service_token):  # your auth helper (mTLS/OAuth in a real system)
        raise HTTPException(status_code=401, detail="unauthorized")  # no token, no action
    return x_service_token                           # available to the handler if needed

@app.post("/remediations")                           # POST because it changes state
def remediate(req: RemediationRequest, _: str = Depends(verify_caller)):  # auth runs before the body is used
    if req.incident_id in COMPLETED:                 # Kafka redelivered or the agent retried
        return COMPLETED[req.incident_id]            # return the earlier result; never act twice
    cmd = RUNBOOK[req.action] + ["--node", req.node_id]  # argument list, so no shell parsing happens
    proc = subprocess.run(cmd, capture_output=True, text=True, timeout=300)  # bounded runtime
    result = {"ok": proc.returncode == 0,            # success flag for the validation agent
              "stderr": proc.stderr[-2000:]}         # truncate: don't return or log megabytes
    COMPLETED[req.incident_id] = result              # record before returning, for idempotency
    return result                                    # FastAPI serializes the dict to JSON
say thisAn allow-list beats a deny-list, the schema is the first security control, idempotency is mandatory once Kafka is involved, and every call has a timeout.
diagnosis_consumer.py · neither loses nor double-processes
import json                                          # safe deserialization (never pickle)
from confluent_kafka import Consumer, Producer       # standard Python Kafka client

consumer = Consumer({
    "bootstrap.servers": "kafka:9092",               # broker address
    "group.id": "diagnosis-agent",                   # one group per agent role; add instances to scale
    "enable.auto.commit": False,                     # BUG FIX: auto-commit can mark a message done before it's processed
    "auto.offset.reset": "earliest",                 # a brand-new group starts from the oldest event
})
producer = Producer({"bootstrap.servers": "kafka:9092",
                     "enable.idempotence": True})    # no duplicate writes on producer retries
consumer.subscribe(["build.events"])                 # input topic, partitioned by node_id

seen: set[str] = set()                               # demo dedupe store; Redis with a TTL in production

try:
    while True:                                      # long-running consume loop
        msg = consumer.poll(1.0)                     # wait up to 1 s for the next message
        if msg is None:                              # nothing arrived this interval
            continue                                 # poll again
        if msg.error():                              # broker or partition error, not a bad payload
            print(f"kafka error: {msg.error()}")     # use structured logging in real code
            continue                                 # the client retries transient errors itself
        try:
            event = json.loads(msg.value())          # bytes -> dict; bad JSON raises and goes to the DLQ
            if event["event_id"] not in seen:        # at-least-once delivery means duplicates happen
                result = diagnose(event)             # your business logic / LLM call, with its own timeout
                producer.produce("incident.diagnosed",   # hand off to the next agent
                                 key=event["node_id"],   # same key keeps per-node ordering downstream
                                 value=json.dumps(result))
                producer.flush()                     # make sure it's written before committing input
                seen.add(event["event_id"])          # mark processed only after the output is durable
        except Exception:                            # poison message: don't block the partition forever
            producer.produce("build.events.dlq", key=msg.key(), value=msg.value())  # park for review
            producer.flush()                         # DLQ write must land before we move on
        consumer.commit(message=msg, asynchronous=False)  # commit only after success or DLQ
finally:
    consumer.close()                                 # leave the group cleanly so partitions rebalance fast
say thisCommit after the side effect, idempotent handling instead of exactly-once transactions, a DLQ so one bad message can't stall a partition. flush() per message is safe but slow; batch it if throughput matters.
log_window.py · trim the log before the LLM sees it
import re                                            # regular expressions
from collections import deque                       # fixed-size buffer with O(1) append

ERROR_RE = re.compile(r"ERROR|FATAL|BUILD FAILED|exit code [1-9]")  # compiled once, not per line

def first_error_window(path: str, before: int = 20, after: int = 20) -> list[str]:
    context = deque(maxlen=before)                   # remembers only the last `before` lines
    with open(path, errors="replace") as f:          # bad bytes won't crash the parser
        for line in f:                               # streams the file; never f.read() a huge log
            if ERROR_RE.search(line):                # the FIRST error is usually the root cause
                window = [*context, line]            # lead-up lines plus the error line
                for _ in range(after):               # collect a fixed number of lines after it
                    nxt = next(f, None)              # continue from the same position in the file
                    if nxt is None:                  # reached end of file
                        break                        # stop collecting
                    window.append(nxt)               # add the trailing line
                return window                        # ~41 lines instead of the whole log
            context.append(line)                     # not an error: keep it as possible context
    return list(context)                             # no match: return the log's tail
say thisThis is the cost-vs-context-window tradeoff in code: fewer tokens, lower latency, less noise for the model to latch onto.

DiagnosisPanel.jsx · streaming an agent's diagnosis safely
import { useEffect, useState } from "react";           // React hooks used below

export function useStreamingDiagnosis(incidentId) {     // custom hook: owns the stream's lifecycle
  const [text, setText] = useState("");                  // accumulated streamed text
  const [status, setStatus] = useState("idle");          // idle | streaming | done | error

  useEffect(() => {
    if (!incidentId) return;                             // nothing selected yet, so don't fetch
    const controller = new AbortController();            // lets us cancel the request on cleanup
    setText("");                                         // clear output from the previous incident
    setStatus("streaming");                              // drives the loading UI

    (async () => {                                       // effects can't be async, so use an inner IIFE
      try {
        const res = await fetch(
          `/api/incidents/${encodeURIComponent(incidentId)}/diagnosis`,  // our backend, never the LLM directly
          { signal: controller.signal, credentials: "include" }          // abortable; session cookie, no API key
        );
        if (!res.ok) throw new Error(`HTTP ${res.status}`);  // treat 4xx/5xx as errors
        const reader = res.body.getReader();             // read the response body as a stream
        const decoder = new TextDecoder();               // bytes -> text
        while (true) {                                   // read until the server closes the stream
          const { done, value } = await reader.read();   // next chunk of bytes
          if (done) break;                               // stream finished
          const chunk = decoder.decode(value, { stream: true });  // handles characters split across chunks
          setText(prev => prev + chunk);                 // BUG FIX: functional update avoids stale state
        }
        setStatus("done");                               // stream completed normally
      } catch (err) {
        if (err.name !== "AbortError") setStatus("error");  // aborts from cleanup are expected, not errors
      }
    })();

    return () => controller.abort();                     // BUG FIX: cancel when the incident changes or unmounts
  }, [incidentId]);                                      // re-run only when the selected incident changes

  return { text, status };                               // the component only sees state, not stream details
}

export function DiagnosisPanel({ incidentId }) {
  const { text, status } = useStreamingDiagnosis(incidentId);  // subscribe to the stream
  return (
    <section aria-busy={status === "streaming"}>         {/* accessible loading state */}
      <pre style={{ whiteSpace: "pre-wrap" }}>{text}</pre>  {/* rendered as text, so model output can't inject HTML */}
      {status === "error" && <p role="alert">Stream failed. Retry.</p>}  {/* visible failure */}
    </section>
  );
}

Under pressure: Restate, Trace, Rank, Prove

  1. RestateSay what the code should do, its inputs and outputs. It buys thinking time and catches misreads. About 30 seconds.
  2. TraceWalk the happy path once, then the edges: empty input, an error mid-way, a duplicate message, concurrent calls, a huge input.
  3. RankName everything, then fix in order: correctness, security, reliability, performance, readability. "I'll note the naming, but fix the data loss first."
  4. ProveRun it or write one quick test for the bug you fixed, then explain the tradeoff you made.

Questions to ask the panel

One per interviewer if time is short. Each signals you're already thinking like the owner of this platform.

  1. Autonomy and blast radius

    "Where is the line today between what the agent fixes on its own and what needs a human? Is it set per action type, per node pool, or by model confidence, and how do you roll back a remediation that made a node worse?"

  2. Evaluation and the learning loop

    "How do you measure whether the agent's root-cause call was right? Is there a labeled set of historical build failures to replay as an offline eval before a new agent or prompt version ships, and does the resolution memory feed back into it?"

  3. Data path and constraints

    "With the build farm on-prem and Azure OpenAI in the loop, what's the biggest bottleneck right now: getting clean log and node-metric signal into Kafka, the latency or cost of model calls, or the approval path to act on production build infrastructure?"
